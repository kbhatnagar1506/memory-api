## 1. MARKET MAP

**Mem0** — LLM fact-extraction into a vector(+graph) store; the shipping platform has drifted to ADD-only append writes with async "Dream" consolidation, no longer matching the ADD/UPDATE/DELETE/NOOP paper it markets on. Token pitch: ~7K tokens/conversation vs ~26K full-context, ">90% savings" **[V]** — baseline is full-context stuffing, and write-side LLM calls are excluded. Benchmark standing: paper numbers are real (J=66.88/68.44 **[I: verified against the paper's tables]**) but the paper's own full-context baseline scores 72.90 — Mem0 loses to pasting the transcript **[I]**; the marketed "+26%" is vs OpenAI Memory (52.90), one of the weakest baselines; the 92.5 platform claim is unreconciled, platform-only, unreproduced **[V]**; Letta got 74.0% on LoCoMo with a filesystem and grep **[I-ish: competitor-run]**. Pricing: free / $19 / $249 / enterprise; audit logs and on-prem are Enterprise-gated. Principal weakness: lossy-by-construction extraction plus benchmark marketing that its own paper contradicts; best-funded ($24M) and best-distributed (AWS Agent SDK) player regardless.

**Zep/Graphiti** — bi-temporal knowledge graph (four timestamps per edge, invalidation not deletion) with hybrid BM25+vector+graph retrieval and no LLM in the read loop. Token pitch: ~1.6K retrieved tokens vs ~115K full-context on LongMemEval **[V]**. Benchmark standing: LongMemEval 71.2% vs 60.2% full-context (gpt-4o) is accurately reported but never independently replicated, and later self-reported systems (Emergence plain RAG at 86%) place it mid-table **[V]**; DMR 94.8% is meaningless — Zep's own full-context baseline scores 94.4–98.0%, a delta of ~2 questions in 500 **[I: from Zep's own paper]**; LoCoMo score is contested in both directions (58.44 vs 75.14) **[C]**. Sub-200ms p95 at 100M graphs **[V]**. Pricing: ingestion credits, $125/$375/mo, $13K/yr startup tier; compliance is Enterprise-gated. Principal weakness: cloud-only since CE deprecation, thin publicized funding (~$500K seed on record), and every headline number self-reported — but it is the incumbent for the "auditable/temporal" story.

**Letta (MemGPT lineage)** — agent self-edited memory, now MemFS: git-backed markdown filesystem with background "dreaming" subagents; no embeddings in the default path. Token strategy: fixed in-context budget + just-in-time file reads; sleep-time compute claims (~5x test-time compute reduction) are from math benchmarks, not memory workloads **[V-adjacent]**. Benchmark standing: its 74.0% LoCoMo-with-grep result is the most damaging single data point against extraction-based memory. Pricing: $20/mo Pro, $0.10/active agent on API plan. Principal weakness: architecture churn (blocks→MemFS), no semantic search by default, no compliance surface at all — zero SOC 2, SSO, or audit-log product documented.

**Supermemory** — closed-source hosted "memory engine" (vector-graph hybrid + profiles) with an MIT client stack and its own benchmark harness (MemoryBench) on which it ranks #1 **[V, circular]**; SMFS claims (55% cheaper, 81% vs 69% accuracy) are on xAFS, a benchmark it invented for the launch **[V]**. Sub-300ms retrieval, no percentile given **[V]**. Pricing: $0–$399/mo + usage, deduplicated "SM tokens." Principal weakness: $2.6M seed vs Mem0's $24M and Engram's $98M; the accuracy/latency claims are about the closed part of the product.

**Others** — Hindsight (Vectorize): 91.4% LongMemEval self-run **[V]**, MIT, human-memory framing. Cognee: graph-ECL, $7.5M. mem-agent (Dria): 4B local model as memory sidecar, own benchmark only. Engram: $98M parametric anti-retrieval bet. LangMem: no benchmarks at all, incomplete episodic memory, LangGraph lock-in. Structural fact **[I]**: the one independent cost-performance study (arXiv 2603.04814) found long-context + prompt caching beats fact-extraction memory on factual recall on LongMemEval and LoCoMo, with memory winning on cost only after ~10 turns at 100K context. That is the sword hanging over this entire category — and it favors *lossless* architectures like ours.

## 3. TOKEN REDUCTION PLAN (target: 2,530 tokens/query)

Ranked by (expected savings × confidence) ÷ implementation cost. Our architecture — raw turns + read-time windowing — means all leverage is at read time; we pay no write-side LLM tax and should keep it that way.

1. **Supersession-aware read filtering** (use what we built). Exclude turns transitively superseded as of query time from the window. Cost: days — the supersession graph exists. Savings: workload-dependent, but any duplicated/corrected content is pure waste; estimate 10–25% on churn-heavy users → **~2,530 → 1,900–2,280**. Quality risk: near-zero (superseded content is by definition stale) and it *improves* temporal-question accuracy. No published isolated dedup numbers exist (research gap noted in token_techniques), so instrument and publish ours.

2. **Turn-encoding compaction**. Strip speaker boilerplate, verbose timestamps, JSON scaffolding; delta-encode session headers. Cost: days. Savings: typically 10–20% of raw transcript tokens → compounding on #1, **→ ~1,600–2,050**. Quality risk: none if timestamps survive in compact form (we need them for bitemporal answers).

3. **Precision-first windowing via hybrid retrieval**. Add BM25 fusion (RRF) so we can shrink k/window rather than over-fetch. Zep's read path and Mem0's 2026 3-signal fusion both do this **[V]**; infra research confirms tsvector is not BM25 (no IDF). Cost: 1–2 weeks (pg_textsearch, or app-side BM25; see §5 on ParadeDB's AGPL). Savings: if precision@k rises enough to halve window size, **→ ~1,000–1,300** at equal-or-better accuracy. Quality risk: low-moderate; measurable on our existing harness. This is the only technique that can raise the 59% *while* cutting tokens.

4. **Extractive read-time compression (LLMLingua-2 class)**. Token-classifier pruning of the assembled window: 2–5x task-agnostic at near-parity, peer-reviewed (ACL 2024 Findings) **[I]** — the honest ratio, not the 20x CoT best case. Applied after #1–3: **→ ~400–800**. Cost: 2–4 weeks (XLM-RoBERTa-large inference in the read path; adds ~10–50ms — budget against our 49ms). Quality risk: moderate; LongLLMLingua's accuracy *gains* came from noisy retrieval, so with clean retrieval expect parity, not improvement. Gate behind an eval.

5. **Recursive session summaries as a fallback tier** (summarize sessions older than N days into bounded summaries, keep raw turns for drill-down). Cost: weeks; introduces our first write-side LLM dependency. Savings: bounds worst-case window growth rather than cutting the average. Quality risk: **high** — arXiv 2603.04814 **[I]** shows exactly this kind of hard compression losing recall to raw replay. Only do it with raw turns retained and summary provenance links (our explain traces make this safe-ish). Rank last; possibly never.

**Do not do**: soft-token/gisting compression (requires finetuning the serving model — unusable against closed APIs); write-time fact extraction (abandons our lossless differentiator and walks into the 2603.04814 recall trap).

**Caching interaction (economics, not tokens)**: cached input reads cost ~0.1x at all three providers **[I: verified from provider docs 2026-08-08]**. Per-query dynamic compression (#4) breaks prefix-cache identity. Assemble context as: stable per-user profile prefix (cacheable, cheap) + volatile compressed tail. A 2,530-token context at 0.1x effective pricing on its stable half can beat a 1,000-token fully-dynamic context on cost — model this before shipping #4; #1–#3 are unambiguous wins either way.

## 4. DIFFERENTIATION THESES

**Thesis A — "Replayable memory": per-decision forensic reconstruction.** *The agent-memory layer that can prove what the agent knew, retrieved, and why, at any past moment — and prove deletion propagated.* Zep has fact-level bitemporality but, per the enterprise research, **no vendor demonstrates reconstruction of the full retrieval context behind a specific past agent decision, and none offers erasure-with-proof that propagates to derived facts** — the named whitespace. Why incumbents can't easily copy: Mem0's append-only platform discarded synchronous supersession and its consolidation is async fire-and-forget — retro-fitting decision-time replay onto that is an architecture rewrite; extraction-based systems can't prove erasure propagation because derived facts have fuzzy lineage; Letta's git history covers memory files, not retrieval decisions. What we have: bitemporal versions + transitive supersession + **per-result explain traces** (the decision-level artifact nobody else ships) + raw-turn storage (lossless provenance) + dual-backend conformance (credible for BYOC/on-prem). Missing: SOC 2 Type II, ABAC, legal hold, retention policies, exportable Article-12-shaped logs, an erasure-proof API. Fastest proof point (2–3 weeks): a demo + short paper — "replay query Q as of time T": exact retrieved set, ranks, explain traces, then delete a source turn and cryptographically attest that it and everything transitively superseded-by/derived-from it is gone from all future and *reconstructed-past* results. No competitor can run this demo today.

**Thesis B — "Honest benchmarks, lossless memory": the credibility position.** *No LLM in the write path, nothing discarded, every number reproducible from our public harness.* Supported by: our harness (commit 51d02a7), interleaving guards (e1b69ea), dual-backend conformance; amplified by the field's credibility crater (Mem0-Zep war, 45-point vendor-vs-independent gaps, LoCoMo audit). Why hard to copy: incumbents' marketing is sunk-cost-committed to disputed numbers, and "lossless" is architecturally false for extraction systems. Missing: our accuracy (59%) must reach ~70%+ before honesty is a flex rather than an excuse. Proof point: publish our full triple (accuracy/latency/tokens) with the answerable-subset methodology and invite reruns.

**Thesis C — "The cache-native economy layer".** *Lean into 2603.04814: raw turns + windowing + stable cacheable prefixes = long-context recall quality at fixed-memory cost.* Zero write amplification (real cost advantage vs Mem0/Zep's per-message LLM ingest, which Zep literally bills on). Why copyable-resistant: extraction vendors' unit economics depend on write-side processing. Missing: a published TCO model; and this is a feature-of-A/B more than a standalone company.

**Winner: A**, with B's harness as its evidence engine. Reasoning: (1) it is the only thesis where our four existing oddball assets — bitemporal versions, transitive supersession, explain traces, dual-backend — stop being engineering nice-to-haves and become the moat; (2) the regulatory clock is running now (AI Act Art. 12 in full application as of 2026-08-02, FINRA 25-07/2026 report), and demand is documented (litigated retention: OpenAI-NYT order, €15M/€5M Garante fines); (3) it monetizes at enterprise price points where our latency edge and BYOC story matter and where our LoCoMo deficit matters least — an auditor does not care about 8 points on a benchmark with 6.4% wrong answers; (4) B alone is not a business and C alone is a feature. Caveat to manage: Gartner's governance-spend forecast is only $492M for 2026, and Zep occupies the adjacent word "temporal" — so the pitch must be the *demo* (decision replay + erasure proof), never the adjective "auditable."

## 5. INFRA VERDICT

**Stay on pgvector.** Our 49ms search is already below every competitor's *claimed* latency, our supersession model is append-only invalidation (bitemporal flags, not row deletes), which sidesteps pgvector's worst failure mode — HNSW's non-reclamation of deleted space — and dual-backend conformance means a later migration is cheap optionality we've already paid for.

Adopt now:
- **pgvector 0.8.x iterative index scans** (`relaxed_order`, tuned `max_scan_tuples`) — this is the fix for exactly our query shape (tenant_id + agent_id + `valid_at`-window predicates); pre-0.8 filtered scans silently under-return, which could be quietly costing us accuracy points today.
- **`halfvec`** (fp16): halves index/storage, raises the HNSW dim cap to 4,000; near-free.
- **BM25 for the §3 hybrid plan**: prefer Timescale **pg_textsearch** (no phrase queries yet) or app-side BM25 over ParadeDB pg_search — pg_search is **AGPLv3**, a real license risk for a commercial API, and unavailable on hyperscaler managed Postgres.
- Operational guardrails: maintenance_work_mem sized to index (≤50–60% RAM) for builds; scheduled `REINDEX CONCURRENTLY` as insurance if we ever hard-delete (erasure-proof API will!).

Scale thresholds (rules of thumb, memory-economics-driven, not cliffs — all from vendor/consultancy sources): comfortable to **~5–10M vectors/node** at 1,536-dim; at that point add **binary quantization + rescore** (~97% index-size reduction on the coarse pass **[V: dbi-services, 25K rows — small-scale evidence]**) and partition by tenant. At **~50M+**, pgvectorscale (StreamingDiskANN, label filters) — but note it does **not** run on RDS/Aurora/Cloud SQL/Supabase, so it implies self-hosted or Tiger Cloud; its 28x-vs-Pinecone numbers are 2024 vendor claims against Pinecone's retired pod tiers **[V, stale]** — treat as directional only. Only past ~100M vectors (>600GB raw) or a many-cold-tenant multi-region requirement does a dedicated engine earn its complexity; turbopuffer's economics are attractive there but its 874ms cold-query p50 **[V]** is disqualifying for a sub-50ms memory API unless tenants are session-warm.

One flag for Thesis A: the erasure-proof API means real deletes, which reintroduces HNSW bloat — design erasure as tombstone-then-batched-REINDEX from day one.
